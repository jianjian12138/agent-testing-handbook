# 01 · 认知迁移：从自动化测试到 Agent 测试

> 目标：一天内完成心智模型换血。读完你应该能用自己的话，向老板解释"为什么 Agent 不能用老办法测"。

---

## 1.1 四个根本性差异

### 差异一：输出是**分布**，不是**值**

传统测试的世界观：
```python
assert calculate_tax(1000) == 150   # 永远成立，否则就是 Bug
```

Agent 的世界观：
```python
result = agent.run("帮我算一下 1000 元的税")
# 第一次："您需要缴纳 150 元税款。"
# 第二次："税额为 ¥150。"
# 第三次："根据现行税率，1000 元对应的税是 150 元，计算方式是 1000 × 15%。"
# 三次都对，但字符串完全不同
```

**影响**：
- `assertEqual` 报废，`assertIn` 也不够用（"税额为 ¥150" 里没有 "150 元"）
- 你需要**语义等价判断**，这就是 LLM-as-Judge 存在的理由
- 单次执行的结果没有意义，必须**跑 N 次看分布**

### 差异二：过程比结果更重要

这是最反直觉的一点。

**真实案例（AWS 旅行规划 Agent）**：
```
响应质量得分：83.9%   ✓  看起来很好
工具参数准确性：64.5%  ✗
忠实度（Faithfulness）：32.3%  ✗✗✗  严重问题
```

Agent 在工具返回空结果时，**有近 7 成概率直接编造数据**——航班价格、气温、汇率，全是瞎说的。用户看到的是一个流畅、自信、格式完整的回答。

**如果只看最终输出，这个问题永远发现不了。**

**影响**：你的测试必须能"看见"Agent 的内部执行过程——调了哪些工具、传了什么参数、工具返回了什么。这就是 **Trace（轨迹）** 的价值。

> 对照理解：这就像你测一个下单接口，不能只看最后返回 `{"code":0}`，还要看它有没有真的扣库存、有没有写流水。只不过 Agent 的"内部调用链"是动态生成的，你事先不知道它会怎么走。

### 差异三：错误会传播和放大

Agent 是多步执行的。第 1 步理解意图偏了一点，第 3 步工具选错，第 5 步就彻底跑偏。

```
用户："帮我查下上个月华东区的退货率"
Step 1  意图识别 → 理解成"查退货订单列表"   ← 小偏差
Step 2  工具选择 → 调用 query_orders          ← 顺着错
Step 3  参数构造 → region="华东", month=7     ← 参数对的
Step 4  数据聚合 → 返回了 3000 条订单明细     ← 数据量爆炸
Step 5  生成回答 → 上下文超限，截断，胡编了一个 4.2%  ← 幻觉
```

最终输出一个数字，看起来"完成了任务"。实际上第 1 步就错了。

**影响**：需要**组件级评测**——对每一步单独打分，才能定位到底哪一环崩的。

### 差异四：没有通用基准

你做客服 Agent，我做代码 Agent，他做研究 Agent——"好"的定义完全不同。

- 代码 Agent：代码能跑、测试能过 → 客观、易测
- 客服 Agent：工单关了吗？语气好吗？10 轮内解决了吗？→ 多维、部分主观
- 研究 Agent：报告质量？引用可信吗？覆盖全吗？→ 高度主观，且基准事实会过期

**影响**：不存在"拿来即用"的 Agent 测试方案。你必须为每个业务场景**定制指标和数据集**。这恰恰是你作为测试专家的价值所在。

## 1.2 术语对照表（贴墙上）

| 传统自动化测试 | Agent 测试 | 说明 |
| --- | --- | --- |
| Test Case | **Task（任务）** | 一个有明确输入和成功标准的测试单元 |
| 一次执行 | **Trial（试验）** | 同一 Task 要跑多次，因为输出非确定 |
| Assertion / 断言 | **Grader（评分器）** | 一个 Task 可以有多个 Grader，输出的是分数不是布尔值 |
| 执行日志 | **Transcript / Trace（记录/轨迹）** | 完整的思考、工具调用、观察、输出 |
| 测试套件 | **Evaluation Suite（评估套件）** | 衡量某个特定能力的一组 Task |
| 测试数据 | **Dataset / Golden（数据集/黄金样本）** | `Golden` = 输入 + 参考答案 + 期望工具链 |
| 预期结果 | **Reference Output / Expected Trace** | 参考输出 + 参考执行轨迹 |
| 通过率 | **pass@k / pass^k** | 见下节，这是最重要的新概念 |
| Mock / 挡板 | **E2E_MOCK 模式 / 沙箱** | 拦截工具调用注入固定返回，保证可复现 |
| 冒烟测试 | **回归评估（Regression Eval）** | 应该接近 100% 通过 |
| 探索性测试 | **能力评估（Capability Eval）** | 应该有一定失败率，否则没区分度 |
| 质量门禁 | **Quality Gate** | 概念完全一致，只是断言换成了指标阈值 |
| 缺陷分析 | **归因（Attribution）** | 定位是感知/规划/记忆/工具哪个模块的问题 |
| 线上监控 | **在线评测（Online Eval）** | 对生产流量抽样打分 |

---

## 1.3 最重要的新概念：pass@k 与 pass^k

因为输出非确定，"通过率"这个词在 Agent 测试里被拆成两个指标。

同一个 Task 跑 5 次，3 次通过：

| 指标 | 含义 | 本例数值 |
| --- | --- | --- |
| **pass@k** | k 次尝试里**至少 1 次**成功的概率 | pass@5 高（有成功的） |
| **pass^k** | k 次尝试**全部**成功的概率 | pass^5 = 0（没全过） |

**怎么选**：

| 你的 Agent 是 | 用哪个 | 为什么 |
| --- | --- | --- |
| 辅助工具，用户可以重试（代码生成、文案生成） | **pass@k** | 用户点一下"重新生成"就行，一次成功就够 |
| 直接面向用户/自动执行（客服、自动工单处理） | **pass^k** | 用户不会接受"你再问一遍"，每次都必须靠谱 |

**实战用法**：
- 开发阶段看 `pass@k` —— **能不能做到？**（能力上限）
- 上线前看 `pass^k` —— **稳不稳定？**（可靠性下限）
- 如果 `pass@5` 很高但 `pass^1` 很低 → Agent 有能力但不稳定，去优化 Prompt 的确定性、降 temperature、加约束

> **这是你和普通测试拉开差距的第一个知识点。** 大部分人还在报"通过率 80%"，你要能说清楚"pass@3 = 92%，但 pass^1 只有 61%，面向用户的场景不能上"。

## 1.4 能力评估 vs 回归评估：必须分开

这是 Anthropic 强调的一个关键区分，很多团队没意识到。

| | 能力评估（Capability Eval） | 回归评估（Regression Eval） |
| --- | --- | --- |
| 问的问题 | Agent **能做什么**？ | Agent **还能做它以前能做的事吗**？ |
| 期望通过率 | 50%~70%（**应该有失败**） | 接近 100% |
| 用例来源 | 专门挑 Agent 做不好的任务 | 已经修复过的 Bug、核心业务场景 |
| 通过率 100% 意味着 | **题目太简单了，该换难的**（评测饱和） | 正常，符合预期 |
| 一旦失败 | 正常，是改进信号 | **是回归，立刻排查** |

**混在一起的后果**：你改了个功能，整体通过率从 70% 升到 75%，看起来变好了。实际上是能力评估涨了 8 个点，回归评估掉了 3 个用例——你引入了回归却不知道。

> 对照理解：这就是你熟悉的「新功能测试」和「回归测试集」的区别，只不过在 Agent 里，前者**允许并且应该**有失败率。

---

## 1.5 评测饱和（Evaluation Saturation）

当你的评测套件通过率连续几个版本都在 95% 以上——**这套评测已经废了**。

它只能追踪回归，无法再提供改进信号。

**处理方式**：
1. 把当前套件降级为「回归评估集」，保持高通过率
2. 开发更难的任务组成新的「能力评估集」：多步骤任务、跨工具协作、更极端的边缘情况
3. 定期（建议每月）检查饱和度

> 对照理解：类似你的自动化用例集跑了两年从来不红，那说明它已经不发现 Bug 了，只是在浪费机器时间。区别是 Agent 领域这个过程快得多——一次模型升级就可能让整套评测饱和。

## 1.6 一张图理清 Agent 测试的三层结构

```
                    ┌─────────────────────────────────────┐
   第三层           │        生产监控 Online Eval          │
   （被动，真实）   │  OTel 追踪 → 抽样打分 → 告警 → 回流   │
                    │  发现"你没想到的场景"                │
                    └─────────────────────────────────────┘
                              ↑ 失败用例回流
                    ┌─────────────────────────────────────┐
   第二层           │      组件级评测 Component Eval       │
   （白盒，归因）   │  感知/规划/记忆/工具 逐模块打分        │
                    │  回答"到底哪一步坏了"                │
                    └─────────────────────────────────────┘
                                      ↑
                    ┌─────────────────────────────────────┐
   第一层           │       端到端评测 E2E Eval            │
   （黑盒，快速）   │  只看输入输出，任务成功率            │
                    │  回答"整体好不好"                    │
                    └─────────────────────────────────────┘
```

**三层不是三选一，是叠加使用**——Anthropic 称之为「瑞士奶酪模型」：每层都有漏洞，但叠在一起能挡住大多数问题。

各层的能力边界：

| 方法 | 优势 | 致命局限 |
| --- | --- | --- |
| 离线评测（1+2 层） | 快、可复现、不影响用户、可进 CI | **只能测你想到的场景** |
| 生产监控（3 层） | 揭示真实用户行为，发现意外问题 | 被动，问题到达用户后才知道 |
| A/B 测试 | 衡量真实业务结果 | 慢，只能测已部署的变更 |
| 用户反馈 | 发现完全没预料的问题 | 稀疏，只反映严重问题 |

## 1.7 心态调整：接受"没有绝对正确"

这可能是转型中最难的一关。

传统测试里，一个 Bug 就是一个 Bug，可以复现、可以定位、可以修复、可以验证。

Agent 测试里：
- 同一个用例，今天过，明天不过，**不一定是 Bug**（可能是采样随机性）
- 你的评分器（LLM Judge）**自己也会出错**，需要用人工来校准评分器
- 一个"失败"可能是 Agent 错了，也可能是**你的评分标准错了**

所以 Anthropic 反复强调一件事：

> **Read the transcripts. Read the transcripts. Read the transcripts.**
> 不阅读记录，你不知道评分器是否在正常工作，也不知道失败是否"公平"。

**新增的工作习惯**：
- 每次评测跑完，**抽样人工阅读 10–20 条失败记录**
- 判断：这是 Agent 真的错了，还是评分器误判了？
- 前者去改 Agent，后者去改评分器

这个动作在传统自动化里叫"分析失败用例"，在 Agent 测试里它的重要性提升了一个数量级——因为**评分器本身是可能出错的被测对象**。

## 1.8 你的技能迁移清单

现在把你的老本行和新工作对上号，做一个自评：

| 你的老技能 | 在 Agent 测试里怎么用 | 需要补什么 |
| --- | --- | --- |
| 等价类/边界值划分 | 设计数据集分层：正常场景 / 边界 / 对抗 | 学会"语义边界"（模糊表达、多意图、话题跳转） |
| 场景法/流程图法 | 设计多轮对话用例、多步骤任务用例 | 学会标注 `expected_trace`（期望的工具调用链） |
| pytest / 参数化 | DeepEval 就是 pytest 插件，直接复用 | 学 `LLMTestCase` / `Golden` / `Metric` 三个概念 |
| Mock / 挡板服务 | Agent 的 `E2E_MOCK` 模式、工具沙箱 | 学会 Mock LLM 响应本身（不只是 Mock 下游） |
| Jenkins / GitHub Actions | 评测流水线，概念完全一致 | 学会设"指标阈值"而非"用例通过" |
| 测试报告平台 | Agent 测试平台的报告模块 | 加上 Trace 回放、指标趋势、成本看板 |
| 性能测试（JMeter） | Agent 的延迟/Token/成本指标 | 学会 TTFT（首 Token 延迟）、Token 效率等新指标 |
| 安全测试 | 红队测试、提示注入、越狱、PII 泄露 | 学 Giskard / promptfoo redteam |
| 缺陷管理 | 失败模式库（Failure Mode Taxonomy） | 建立"失败模式 → 改进方向"映射表 |

**你缺的其实只有三样**：
1. LLM/Agent 的工作机制（3 天）
2. 评分器设计手艺（贯穿全程，是核心）
3. 一点 Python + 一点可观测性技术栈（你大概率已有）
