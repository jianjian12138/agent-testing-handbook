# 08 · 实战项目：5 个练手项目从 0 打到平台

> 这是文档的"发动机"。前面 7 篇是理论，这一篇是**你每周要交的作业**。每个项目都能跑、能测、能写进简历。
> 5 个项目对应 5 个能力台阶，串起来正好是"从会测单个 Agent → 会搭测试平台"。

---

## 项目地图

| 项目 | 名称 | 阶段 | 你要做出的东西 | 对应文档 |
| --- | --- | --- | --- | --- |
| **P1** | Hello Eval | 一(1-2周) | 跑通最小 Agent + 第一条评测 | 02 + 03 |
| **P2** | 开源 Agent 评测 | 二(3-5周) | 给一个真实开源 Agent 写评测集 | 04 + 05 |

## P1 · Hello Eval：跑通最小闭环（第 1–2 周）

**目标**：用最短路径体验"写 Agent → 写评测 → 看它失败 → 修 Agent"的完整闭环。

**你要做的**：
1. 运行 `starter/agent/customer_service_agent.py`（一个约 60 行的裸 Agent，含一个故意留的 Bug）
2. 写 `starter/evals/test_p1_basic.py`，用最朴素的断言验证：
   - 用户问订单 → Agent 调用了 `query_order`
   - Agent 没有编造订单状态（忠实度朴素版：答案里出现的订单字段必须来自工具返回）
3. 触发"空结果陷阱"：问一个不存在的订单，观察 Agent 如何圆谎——你的评测应该**判它失败**
4. 修复 Bug（修 `query_order` 的空结果处理），重跑，看到绿

**交付物**：
- 一条能红能绿的评测用例
- 一份你写的项目笔记：`starter/evals/samples/p1_notes.md`（记录你观察到的非确定性现象）

**验收标准**：能向别人演示"我让一个 Agent 的评测从红变绿"。

> 💡 这个 Bug 是精心设计的——它制造"工具返回空，但 Agent 编了一个状态"。这正好对应文档 03 最关键的 **Faithfulness（忠实度）** 指标。P1 你就亲手踩中了这个坑。

## P2 · 开源 Agent 评测：写真实评测集（第 3–5 周）

**目标**：找一个有代表性的开源 Agent（如 LangChain / AutoGen / 某客服 Agent），**为它设计评测集 + 评分器**，体验文档 04/05 的方法论。

**你要做的**：
1. 选一个你熟悉领域的开源 Agent（建议：客服 / 代码生成 / 数据分析 三选一）
2. 用文档 05 的"数据集三层架构"为它建：
   - `starter/datasets/regression/` ：10 条必须有稳定预期的核心用例
   - `starter/datasets/challenge/` ：10 条能力挑战用例（通过率 50–70%）
3. 实现至少 2 类 Grader（文档 04）：
   - 一个**代码评分器**（工具调用对不对）
   - 一个 **LLM-as-Judge**（用文档 04 的 Prompt 模板，含 confidence 字段）
4. 跑 `pass@k`（k=5），记录 mean / min / max

**交付物**：
- 一套 20 条的数据集（JSON，含 `expected_output` / `expected_trace` / `must_not_fabricate`）
- 2 个评分器代码
- 一份"评测报告"：哪些用例稳定过、哪些非确定、Judge 一致率多少

**验收标准**：能说出"这个 Agent 在 X 类任务上不可靠，因为……"，并且你的 Judge 一致率 ≥ 80%（否则按文档 04 重改 Prompt）。

## P3 · CI 质量门禁：评测进流水线（第 6–8 周）

**目标**：把 P2 的评测接进 CI，做到"评测不过，不许合并"——这是从"会测"到"工程化"的门槛。

**你要做的**：
1. 写 `starter/evals/run_suite.py`：批量跑数据集 + DeepEval（文档 06）
2. 设计**分级准出标准**（文档 03 的 L1/L2/L3）：
   - 核心回归集：L1，必须 100% 过，否则阻断
   - 能力挑战集：L2，通过率跌破基线告警
   - 新指标实验：L3，仅记录
3. 接到 CI（GitHub Actions / GitLab CI 任选）：
   - 每次 PR 跑评测，输出报告
   - 核心指标不达标 → `exit 1` 阻断合并
4. 引入 `E2E_MOCK / E2E_REAL` 双模（文档 01）：Mock 挡板保证 CI 可复现、不烧钱；Real 模式定时跑反映真实

**交付物**：
- 一个能跑的 CI 配置（`.github/workflows/agent-eval.yml` 或等价物）
- Quality Gate 脚本：核心指标阻断、辅助指标告警
- 一份"门禁设计说明"：哪些指标阻断、为什么

**验收标准**：故意让 Agent 改坏一个核心行为，CI 必须红、必须拦住合并。

## P4 · 全链路可观测：生产闭环（第 9–10 周）

**目标**：把测试能力延伸到生产，实现"在线评测 + 失败回流"闭环（文档 07）。

**你要做的**：
1. 给 Agent 套 OTel Span（文档 07.2 模板），接入 Langfuse
2. 写一个**在线评分器**：对采样生产 Trace 跑忠实度 + 工具失败率
3. 写**回流脚本**：扫描忠实度 < 0.8 的 Trace → 导出到 `starter/datasets/candidates/`
4. 配置 3 条告警（忠实度/工具失败率/成本），对应文档 07.6 的 SLO
5. 做一次"人工标定演练"：把 3 条候选 Trace 标成 `expected_output`，进回归集

**交付物**：
- 可观测 Agent 一个（Trace 能在 Langfuse 看到）
- 在线评分 + 回流脚本
- 告警配置 + 一次回流记录

**验收标准**：能演示"生产里发现一个失败 → 它自动进了我的回归集 → 下次 CI 拦住同类问题"。

## P5 · 多 Agent 评测 + 平台原型（第 11–12 周）

**目标**：评测多 Agent 协作，并把前面所有东西整合成一个**最小可用平台原型**——兑现你"搭建自己的 Agent 测试自动化平台"的诉求。

**你要做的**：
1. 搭一个 2–3 个 Agent 协作的小系统（如：规划 Agent + 工具 Agent + 校验 Agent）
2. 用文档 04 的 **Agent-as-Judge** 思路评测：沙箱跑 → 语义切片 → 门禁对抗校验，SubAgent 并行
3. 评测"协作失效"（文档 02 的多 Agent 失效维度）：信息丢失、循环、职责冲突
4. **平台原型**：把 P1–P4 串成一个 Web/CLI 平台（文档 09 的 M1–M6 至少做到 M3）：
   - 数据集管理 + 上传
   - 一键跑评测 + 出报告
   - 看板（通过率趋势、成本趋势）
   - 回流入口

**交付物**：
- 多 Agent 评测报告（含协作失效发现）
- 一个能跑的平台原型（CLI 或 Web 均可）
- 一份"平台架构说明 + 演进路线"

**验收标准**：别人把一个新的 Agent 丢给你平台，你能 10 分钟内配好数据集、跑出报告、给出"能不能发"的结论。

- P1→P3 是硬门槛，必做；P4→P5 是加分项，但 P5 的平台原型是你最终目标，尽量跑到 M3。
