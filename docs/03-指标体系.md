# 03 · 指标体系：测什么

> 目标：3 天。读完你应该能为任意一个 Agent 产品，在 1 小时内产出一份指标定义表 + 准出标准。
> 这是你区别于"会用工具的人"的核心能力。

---

## 3.1 指标设计的三条铁律

在看具体指标之前，先立三条原则。违反了，指标做出来也是废的。

### 铁律一：指标必须与 Agent 架构同构

> 阿里国际的核心经验："**评测指标体系需要和 Agent 架构同构**"

意思是：Agent 有几个模块，指标就应该分几组。这样一旦某个指标掉了，**能直接映射到优化动作**。

```
意图识别准确率↓  →  去调感知模块的分类 Prompt / 加 few-shot
工具选择准确率↓  →  去改工具描述（description）/ 加使用约束
忠实度↓          →  去加"工具返回空必须告知用户"的系统提示
短期记忆保留率↓  →  去改上下文窗口策略 / 摘要压缩逻辑
```

**反面教材**：只有一个"整体质量分 7.2 分"。掉到 6.8 了，你不知道该改哪。

### 铁律二：指标必须面向行动（Actionable）

每个指标定义完，问自己一句：**"这个指标掉了，我知道该干什么吗？"** 答不上来，这个指标就该删掉。

### 铁律三：每个评测场景只设一个主指标

> **主指标判定法**：每种评测场景设一个主指标（北极星），**只看主指标定 case 通过与否**，其它指标作为短板定位用。

原因：10 个指标里 3 个没过，你不知道优先修哪个。有主指标就有了排序依据。

| 评测场景 | 主指标 |
| --- | --- |
| 端到端 | 任务完成率 |
| 感知模块 | 意图识别准确率 |
| 规划模块 | 工具调用决策准确率 |
| 记忆模块 | 短期记忆保留率 |
| 工具模块 | 工具调用准确率 |
| RAG | 忠实度（Faithfulness） |

## 3.2 三维指标框架：质量 × 成本 × 性能

很多团队只测质量，上线后被成本和延迟打脸。**从第一天就要三维一起测。**

```
              质量 Quality
                   ▲
                   │
                   │
    成本 Cost ◄────┼────► 性能 Performance
```

| 维度 | 为什么必须测 | 典型指标 |
| --- | --- | --- |
| **质量** | 能不能用 | 任务完成率、忠实度、工具准确率 |
| **成本** | 能不能规模化 | 平均模型调用次数、平均工具调用次数、输入/输出 Token 数、单任务费用 |
| **性能** | 用户等不等得起 | 首 Token 延迟（TTFT）、端到端响应延迟、各模块延迟 |

**成本指标的实战意义**：一个准确率 92% 但每次要调 15 次模型的 Agent，和一个准确率 88% 但只调 4 次的 Agent，后者往往才是能上生产的那个。

**性能指标细分**（模块级，用于定位瓶颈）：
意图识别延迟、规划决策延迟、短期记忆注入延迟、长期记忆检索延迟、工具调用延迟、热更新生效延迟。

## 3.3 五维质量指标框架（核心，背下来）

### 维度一：任务完成度（北极星）

| 指标 | 定义 | 说明 |
| --- | --- | --- |
| **端到端任务成功率** | 成功任务数 / 总任务数 | 分三档：L1 严格成功 / L2 基本成功 / L3 失败 |
| 目标达成率 | 完成的子目标数 / 总子目标数 | 例：3 个子目标完成 2 个 = 66.7% |
| 输出可用率 | 可直接使用的输出比例 | 代码：可运行率；文档：可直接发布率 |
| 多轮对话完成率 | 多轮任务中完成的比例 | 多轮场景专用 |

**生产基线参考**（可以直接拿去和产品经理谈判）：

| 场景 | L1（严格成功） | L1+L2（基本可用） |
| --- | --- | --- |
| 代码生成 | ≥40% | ≥75% |
| 文档写作 | ≥60% | ≥85% |
| 数据分析 | ≥50% | ≥80% |

> 看到 40% 别惊讶。SWE-bench 上 Devin 的 resolve rate 是 13.86%。Agent 领域的"及格线"和传统软件完全不是一个量级。**管理好干系人的预期，也是你的工作。**

---

### 维度二：工具使用质量

| 指标 | 定义 | 基线 |
| --- | --- | --- |
| 工具选择准确率 | 调对工具的比例 | 单工具场景 ≥95%，多工具 ≥90%，特定工具 ≥85% |
| 参数准确率 | 按 3/2/1/0 分档打分后归一 | ≥85% |
| 调用链效率 | 最小必要调用次数 / 实际调用次数 | ≥0.6（允许一定探索性调用） |
| 工具调用成功率 | 调用未报错的比例 | ≥98% |

**参数准确率分档标准**（复用文档 02）：
| 分数 | 判定 |
| --- | --- |
| 3 | 完全正确 |
| 2 | 核心参数正确，可选参数有出入 |
| 1 | 部分参数错误，但方向正确 |
| 0 | 完全错误 |

---

### 维度三：规划与推理

| 指标 | 定义 | 基线 |
| --- | --- | --- |
| 规划合理性 | LLM-as-Judge 打 1–5 分（5 分含异常考虑） | ≥3.5 |
| **死循环率** ⚠️ | 触发死循环的任务比例 | 🔴 **生产红线：>2% 必须修复** |
| 错误恢复率 | 遇错后恢复成功数 / 遇错总数 | ≥60% |
| 规划遵循度 | 实际执行是否遵循自述的计划 | ≥0.7 |

**死循环判定规则**：连续 5 次调用同一工具同一参数，**或** 出现 3 次相同的决策模式。

---

### 维度四：SubAgent 协作（多 Agent 场景）

| 指标 | 判定要点 |
| --- | --- |
| 创建时机合理性 | 该并行（独立模块搜索）未用 → 扣分；不该并行（简单单步）却创建 → 扣分 |
| 结果整合质量 | ① 含关键发现 ② 无相互矛盾 ③ 依赖传递正确 ④ 失败有兜底 |

---

### 维度五：安全与效率

| 指标 | 定义 | 红线 |
| --- | --- | --- |
| **危险操作率** | 执行 `rm -rf` / `drop table` / `force push` / 未授权转账等 | 🔴 **0%** |
| **幻觉引入率** | 编造 API、虚构文件内容、捏造数据 | 🔴 **≤3%** |
| 提示注入成功率 | 被用户输入绕过系统提示的比例 | 🔴 0% |
| PII 泄露率 | 输出中泄露用户隐私信息 | 🔴 0% |
| 平均完成时间 | | 简单任务 <30s，复杂任务 <5min |
| 平均费用/任务 | | 按业务定，需要设上限 |

## 3.4 端到端六项用户感知指标

除了模块级，还要有一组"用户视角"的指标：

| 指标 | 定义 | 注意点 |
| --- | --- | --- |
| **任务完成率** | 北极星 | |
| 多轮对话完成率 | 多轮场景是否达成目标 | 需独立 sessionId、轮间等待持久化 |
| 指令遵循能力 | 格式、字数、语言、语气约束是否遵守 | 可用代码评分器精确判定 |
| **幻觉率（忠实性）** | 输出是否忠于检索/工具返回的内容 | ⚠️ **只判"忠实转述"，不判知识源本身对错** |
| 异常输入处理率 | 乱码/超长/空/攻击输入是否优雅处理 | |
| 用户满意度 | 线上点赞率、会话后立即退出率等 | 生产环境采集 |

> 🔑 **幻觉率的定义边界很重要**：Faithfulness 判的是"Agent 有没有忠实转述工具/知识库返回的内容"，**不判断知识源本身是否正确**。知识源错了那是数据治理问题，不是 Agent 的锅。这个边界不划清楚，指标会变成一笔糊涂账。

## 3.5 RAG 环节的四个指标（RAGAS 四件套）

如果你的 Agent 带知识库，这四个必测：

| 指标 | 检查什么 | 定位到哪 |
| --- | --- | --- |
| **Context Recall** 上下文召回 | 该检的都检到了吗 | 检索阶段：切块/embedding/topK |
| **Context Relevancy** 上下文相关性 | 检回来的都有用吗 | 检索阶段：重排/过滤 |
| **Faithfulness** 忠实度 | 答案是否有据可依 | 生成阶段：Prompt 约束 |
| **Answer Relevancy** 答案相关性 | 有没有答非所问 | 生成阶段 |

**排查逻辑**：
```
回答质量差
  ├─ Context Recall 低 → 检索没找到，去优化召回（切块、多路召回、query 改写）
  ├─ Context Relevancy 低 → 检索噪声大，去加重排（rerank）
  ├─ Faithfulness 低 → 检索到了但没用，或者在编，去改生成 Prompt
  └─ 前三个都正常 → 生成能力问题，考虑换模型
```

## 3.6 指标 → 数据集 → 评测范围的映射设计

这是阿里国际方案里最有工程价值的部分：**让评测范围、数据集、指标三者自动装配**，用户选一个范围，系统自动挑数据集、自动筛指标。

**评测范围（15 种）**：
- 端到端评测 ×1
- 核心模块评测 ×1（四模块全跑）
- 分模块评测 ×4（感知/规划/记忆/工具）
- 指定数据集 ×8（见下）

**数据集（8 类）与规模建议**：

| 数据集 | 最小规模 | 评测模式 | 覆盖的主要指标 |
| --- | --- | --- | --- |
| 基础技能集 | ≥50 条（按 Skill 维度） | E2E_MOCK / E2E_REAL | 任务完成率、工具准确率 |
| 知识问答集 | ≥100 条（含负例） | E2E_REAL | 忠实度、RAG 四件套 |
| 多轮对话集 | ≥10 组 | E2E_REAL | 多轮完成率、短期记忆保留率 |
| 异常输入集 | ≥20 条 | E2E_MOCK | 异常输入处理率、降级触发准确率 |
| 工具调用集 | ≥20 条 | E2E_MOCK | 工具选择/参数/成功率 |
| 多意图集 | ≥20 条 | E2E_REAL | 多意图识别率 |
| 模糊意图集 | ≥20 条 | E2E_REAL | 模糊意图澄清率 |
| 长对话衰减集 | ≥10 组 | E2E_REAL | 记忆衰减曲线 |

**两种评测模式**（这个设计很关键，直接抄）：

| 模式 | 做法 | 优点 | 缺点 | 用在哪 |
| --- | --- | --- | --- | --- |
| `E2E_REAL` | 真实 LLM / 真实工具 / 真实 RAG | 反映生产真实表现 | 受外部抖动影响，不可复现 | 版本准出、能力评估 |
| `E2E_MOCK` | 通过 `mockDataId` 关联 Mock 数据，拦截器替换远程调用 | **完全可复现** | 不反映真实链路问题 | 回归评估、Trace 排查、CI |

> 这就是你熟悉的"挡板测试"，在 Agent 领域同样是**可复现性的唯一解**。CI 流水线里必须用 `E2E_MOCK`，否则每次结果都不一样，门禁形同虚设。

## 3.7 分级准出标准（可直接落地）

按**变更风险**分级，不同风险等级跑不同强度的评测。这是你作为质量负责人的核心产出。

### L1 · 低风险变更（改 Prompt 文案、加一条 FAQ）

| 检查项 | 要求 |
| --- | --- |
| 单工具回归集 | 100% 通过 |
| LLM-Judge 主指标 | 不劣化（≥ 基线 - 2%） |
| 执行时长 | <10 分钟（不能拖慢开发） |

### L2 · 中风险变更（模型升级、工具增删、规划逻辑调整）

| 检查项 | 要求 |
| --- | --- |
| L1 全部项 | 通过 |
| 多工具链任务集 | 全量跑 |
| 工具选择准确率 | ≥85% |
| **死循环率** | **= 0%** |
| **危险操作率** | **= 0%** |
| **幻觉率** | **≤3%** |
| 成本 | 不劣化超过 20% |

### L3 · 高风险变更（Agent 框架升级、架构重构、上新业务线）

| 检查项 | 要求 |
| --- | --- |
| L2 全部项 | 通过 |
| 对抗/边界任务集 | 全量跑 |
| 错误恢复率 | ≥60% |
| **人工评审** | 3 人独立评审，**Cohen's Kappa ≥0.6**（一致性达标才有效） |
| 灰度策略 | 5% → 20% → 50% → 100%，每档观察 24h |
| 费用 | 不劣化超过 30% |

> **Cohen's Kappa** 是衡量多人标注一致性的统计量。<0.4 说明评审标准本身有歧义，需要先统一口径再评。这个细节能让你的方案看起来非常专业。

```python
# 快速计算 Cohen's Kappa
from sklearn.metrics import cohen_kappa_score
rater_a = [1, 0, 1, 1, 0, 1, 0, 1]
rater_b = [1, 0, 1, 0, 0, 1, 1, 1]
print(cohen_kappa_score(rater_a, rater_b))   # ≥0.6 才可用
```

## 3.8 一份指标定义表模板（拿走即用）

给每个指标都填这张表，模糊的指标就是没定义的指标。

```yaml
- metric_id: tool_selection_accuracy
  name: 工具选择准确率
  module: 工具模块
  is_primary: false                     # 是否为该场景主指标
  definition: 调用的工具集合与 expected_tools 的匹配程度
  formula: |
    正确调用的工具数 / max(实际调用工具数, 期望工具数)
    多调冗余工具要扣分；漏调必要工具要扣分
  grader_type: code                     # code | llm | human
  data_source: trace.tool_spans
  applicable_datasets: [基础技能集, 工具调用集]
  baseline: 0.90
  gate_level: L2                        # 在哪一级准出中作为门禁
  blocking: true                        # 是否阻断合并
  owner: 张三
  known_pitfall: |
    Agent 常有"以防万一多调工具"的倾向；
    并行调用同一工具多次时，去重后再计数
```

## 3.9 指标选择的实用建议

**别贪多。** DeepEval 官方建议：**单次评测不超过 5 个指标**。

指标选太多的后果：跑得慢、花钱多、结果难解读（10 个指标 3 个没过，不知道先修哪个）。

**按场景的推荐组合**：

| Agent 类型 | 推荐指标组合（3–5 个） |
| --- | --- |
| RAG 问答 Agent | `ContextualPrecision` + `Faithfulness` + `AnswerRelevancy` + 1 个业务自定义 |
| 工具调用 Agent | `ToolCorrectness` + `AgentGoalCompletion` + `Faithfulness` + 1 个业务自定义 |
| 多轮对话 Agent | `ConversationCompleteness` + `AgentGoalCompletion` + 短期记忆保留率 + 1 个业务自定义 |
| 代码 Agent | 测试通过率（代码评分器）+ 静态检查 + `ToolCorrectness` + Token 效率 |

业务自定义指标一律用 `GEval`（自然语言描述评分标准），例如：
- "回答是否包含具体的处理时间预期"
- "是否主动询问了用户的订单号"
- "拒绝时是否给出了替代方案"
