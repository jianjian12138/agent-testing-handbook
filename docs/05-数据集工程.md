# 05 · 数据集工程：用例从哪来

> 目标：4 天。
> **这是你作为资深测试最能发挥优势的一篇**——用例设计是你的老本行，只是换了个载体。
> 也是整个评测体系里最有沉淀价值的资产：**数据集决定评测的覆盖面和上限。**

---

## 5.1 为什么数据集比工具重要

工具三天能学会。数据集需要几个月的持续积累，而且**别人抄不走**——因为它承载的是你对业务的理解。

> **评测系统的核心资产是两样东西：评测数据集 和 评测 Skill（评估器）。**
> 前者定义"评什么"，后者定义"怎么评"。缺一不可。平台只是执行引擎。

一个残酷的现实：**没有覆盖面足够广、边界 case 足够多、参考答案足够准确的数据集，再好的评估器也是空转。**

---

## 5.2 一个必须记住的案例

AWS 工程师评测旅行规划 Agent：

```
响应质量：83.9%   ✓  回答清晰、可操作，用户看起来很满意
      ↓ 深挖追踪数据
忠实度：32.3%     ✗  Agent 在工具返回空结果时，编造汇率、温度、景点详情
```

**这个案例说明两件事**：
1. **测试用例必须覆盖边缘情况**（工具返回空结果就是典型边缘情况）
2. **指标要选对**（光看输出质量不够）

**把它翻译成你熟悉的语言**：这就是"接口返回空数组时前端页面崩了"，只不过 Agent 不会崩，它会**一本正经地编一个**。这比崩溃更危险。

## 5.3 数据集的三层架构

```
┌──────────────────────────────────────────────────────┐
│  Layer 3  对抗/边界任务集      50–100 条              │
│  工具不可用、权限不足、提示注入、超长输入、多意图冲突  │
│  用途：安全 + 鲁棒性，L3 高风险变更必跑                │
├──────────────────────────────────────────────────────┤
│  Layer 2  多工具链任务集       100–200 条             │
│  需要 2+ 工具协作、多步骤、有依赖关系                  │
│  用途：决定能否上线，L2 中风险变更必跑                 │
├──────────────────────────────────────────────────────┤
│  Layer 1  单工具任务集         200–500 条             │
│  单一意图、单一工具、结果明确                          │
│  用途：回归必跑，L1 低风险变更即可触发                 │
└──────────────────────────────────────────────────────┘
```

**同时还要按用途分成两套**（对应文档 01 的能力/回归划分）：

| 数据集 | 期望通过率 | 更新策略 |
| --- | --- | --- |
| **回归测试集** | 接近 100% | 只增不减，修过的 Bug 全部进来 |
| **能力挑战集** | 50–70% | 通过率过高就要加难题（防饱和） |

```python
# 两套数据集，分开跑，分开看
regression_dataset = EvaluationDataset(); regression_dataset.pull(alias="回归测试集")
capability_dataset = EvaluationDataset(); capability_dataset.pull(alias="能力挑战集")
```

## 5.4 八类业务数据集（阿里国际方案，可直接套用）

| 数据集 | 最小规模 | 模式 | 设计要点 |
| --- | --- | --- | --- |
| **基础技能集** | ≥50 条（按 Skill 维度组织） | `E2E_MOCK` + `E2E_REAL` | 每个 Skill 至少 5 条 |
| **知识问答集** | ≥100 条（**必须含负例**） | `E2E_REAL` | 负例示例：问一个知识库里根本没有的接口，看它编不编 |
| **多轮对话集** | ≥10 组（每组 5+ 轮） | `E2E_REAL` | 用 `conversationChain` 串联，含指代、话题跳转、需求变更 |
| **异常输入集** | ≥20 条 | `E2E_MOCK` | 空输入、超长、乱码、纯符号、注入攻击、无关话题 |
| **工具调用集** | ≥20 条 | `E2E_MOCK` | 重点覆盖工具返回空/异常/超时 |
| **多意图集** | ≥20 条 | `E2E_REAL` | "查订单顺便看下物流""退款并且投诉" |
| **模糊意图集** | ≥20 条 | `E2E_REAL` | "我要那个""不行""帮我处理下" |
| **长对话衰减集** | ≥10 组（每组 15+ 轮） | `E2E_REAL` | 开头设约束，20 轮后验证是否还遵守 |

## 5.5 用例的标注格式（Golden 结构）

一条好用例长什么样。**一条数据可以供多个 Judge Task 使用**，所以标注要足够丰富：

```json
{
  "id": "KQA-NEG-004",
  "scene_code": "knowledge_qa_negative",
  "category": "adversarial",

  "input": "IC 服务的 batchQueryProductDetail 接口限流是多少？",
  "conversation_chain": null,

  "expected_skill": "KnowledgeQA",
  "expected_route": "SKILL_MISS",
  "expected_tools": [{"name": "repo_vector_search"}],

  "reference_output": "抱歉，我在知识库中没有找到 batchQueryProductDetail 接口的限流配置信息，建议您联系 IC 服务负责人确认。",
  "expected_knowledge": [],

  "assertions": {
    "must_contain": ["没有找到", "建议"],
    "must_not_contain": ["QPS", "限流为", "每秒"],
    "must_not_fabricate": true
  },

  "eval_mode": "E2E_REAL",
  "mock_data_id": null,

  "reference_trace": [
    {"tool": "repo_vector_search", "params": {"query": "batchQueryProductDetail 限流"}, "result_empty": true}
  ],

  "difficulty": "hard",
  "source": "production_log",
  "created_at": "2026-07-15",
  "owner": "张三",
  "notes": "该接口不存在，用于检测编造行为"
}
```

**字段设计要点**：

| 字段 | 为什么需要 |
| --- | --- |
| `expected_route` | 区分 `SKILL_HIT` / `SKILL_MISS`，用于路由错误跳过逻辑 |
| `must_not_contain` | **负向断言，比正向断言更能抓 Bug** |
| `must_not_fabricate` | 触发 Faithfulness 判定 |
| `reference_trace` | 用于工具链评分器比对 |
| `eval_mode` + `mock_data_id` | 决定跑真实链路还是 Mock 链路 |
| `difficulty` | 用于分层统计，避免"简单题拉高整体分" |
| `source` | 生产日志来的用例价值最高，要能追溯 |

## 5.6 三种构建方式

### 方式一：从生产日志挖（最高价值）

真实用户的输入，比你手写的测试用例真实得多。生产日志里藏着你想不到的边缘情况、奇怪的问法、以及 Agent 真实失败的场景。

**筛选策略**：
- 评测分数低于阈值的
- 工具调用失败/超时的
- 用户反馈差的（点踩、重新提问、立即退出会话）
- 会话轮数异常多的（说明 Agent 没搞定）
- 工具调用次数异常多的（>10 次）
- 响应时间异常长的（>30s）

```python
def extract_failure_cases(log_file, output_file, score_threshold=0.6):
    """从生产日志提取低分用例，加入测试集"""
    failures = []
    with open(log_file, encoding="utf-8") as f:
        for line in f:
            r = json.loads(line)
            if r.get("eval_score", 1.0) < score_threshold:
                failures.append({
                    "input": r["input"],
                    "actual_output": r["output"],
                    "tools_called": r["tools_called"],
                    "eval_score": r["eval_score"],
                    "failure_reason": r.get("failure_reason", ""),
                    "source": "production",
                    "added_at": datetime.now().isoformat(),
                    "expected_output": None,      # ← 待人工标注
                    "status": "pending_review",   # ← 必须人工过一遍
                })
    with open(output_file, "a", encoding="utf-8") as f:
        for c in failures:
            f.write(json.dumps(c, ensure_ascii=False) + "\n")
    return failures
```

**为什么这批用例特别有价值**：它们是 Agent **真实失败过**的场景。用这些做回归测试，能确保修复一个 Bug 之后同类问题不再出现。

> 建议节奏：**每周从生产日志筛选 10–20 条**加入数据集。

### 方式二：合成数据生成（解决冷启动）

刚上线的 Agent 没有历史数据，而且有些边缘情况在生产里出现频率很低——等你收集够样本，可能已经出了很多事故。

```python
from deepeval.synthesizer import Synthesizer

synthesizer = Synthesizer()

# 从文档生成
dataset = synthesizer.generate_goldens_from_docs(
    document_paths=["./docs/product_manual.pdf", "./docs/faq.md"],
    include_expected_output=True,
    max_goldens_per_document=20,
)

# 从上下文定向生成边缘情况（更常用）
dataset = synthesizer.generate_goldens_from_contexts(
    contexts=[["退款政策：30天内可全额退款，超过30天不予退款。"]],
    evolutions={
        "边界情况": 0.4,    # "第31天能退吗"
        "对抗性问题": 0.3,  # "你们的退款政策是骗人的"
        "模糊问题": 0.3,    # "我想退"
    },
    max_goldens_per_context=10,
)
dataset.push(alias="客服 Agent 测试集 v1")
```

**⚠️ 合成数据的致命坑**：
> `expected_output` 是 LLM 生成的，不是人工标注的。**如果你的 Agent 和生成 expected_output 的 LLM 是同一个模型，评测结果会虚高**——两者"思维方式"一样，输出高度相似，但这不代表 Agent 真的做对了。

**解法**：
1. 生成 `expected_output` 的模型，与被测 Agent 用**不同厂商**的模型
2. **必须人工审核**，至少抽查 20–30%，重点看边缘情况和对抗性问题的参考答案是否合理

**中文场景的实用做法**：用一个 Prompt 模板 + 你的业务文档（语雀/Confluence/PRD）批量生成，再人工审核入库。阿里国际就是这么做的——「语雀 URL + 类型 → Prompt 模板生成 → 人工审核入库」。

### 方式三：代码分析生成（AWS Agent-EvalKit 思路）

**让 AI 读你的 Agent 源码，针对代码分支生成用例。** 这是三种方式里最"测试工程"的一种，和你熟悉的白盒测试思路一致。

```bash
uv tool install evalkit --from git+https://github.com/awslabs/Agent-EvalKit.git
evalkit init my-agent-evaluation
cd my-agent-evaluation
cp -r /path/to/your/agent .
claude   # 或其它支持的 AI 编码助手

# 六阶段
/evalkit.plan  评估 ./travel_agent 的忠实度，重点关注工具返回空结果的情况
/evalkit.data       # 生成测试用例
/evalkit.trace      # 添加 OpenTelemetry 追踪
/evalkit.run_agent  # 运行 Agent 收集轨迹
/evalkit.eval       # 计算指标
/evalkit.report     # 生成报告（含代码位置的改进建议）
```

**它的独特价值**：会针对**错误处理路径**专门生成用例。

```python
def get_exchange_rate(from_currency, to_currency):
    result = call_exchange_api(from_currency, to_currency)
    if not result:
        return None     # ← EvalKit 识别出这里没处理空结果
```
→ 自动生成一个"汇率 API 返回空结果"的测试用例，专门测 Agent 在这种情况下会不会幻觉。

**这正是 AWS 工程师发现旅行 Agent 忠实度只有 32.3% 的方式。**

> 💡 **对你的启发**：这个思路完全可以自己实现——让 AI 读 Agent 代码，找出所有 `if not result` / `except` / `return None` / 默认值分支，为每个分支生成一条 Mock 用例。这可以做成你平台的一个功能，是很好的差异化亮点。

## 5.7 完整的数据集建设流程

```
阶段一：冷启动（无生产数据）
  ├─ Agent-EvalKit 分析代码 → 50–100 条（覆盖错误分支）
  ├─ DeepEval Synthesizer 从文档生成 → 50 条
  ├─ 手工从"发布前手动验证清单"提取 → 20–50 条  ← 别忘了这条，价值最高
  └─ 人工审核筛选 + 标注 expected_output
       ↓
  初始数据集：约 120–200 条

阶段二：上线后持续扩充
  ├─ 生产追踪自动收集
  ├─ 每周筛选低分/失败用例 10–20 条
  ├─ 人工标注 → 入库 → 版本 +1
  └─ 每月复盘：检查饱和度，补充难题
       ↓
  数据集持续增长，越来越贴近真实
```

**版本管理**（像管代码一样管数据集）：

```python
from deepeval.dataset import EvaluationDataset, Golden

dataset = EvaluationDataset()
dataset.pull(alias="客服 Agent 测试集 v1")
dataset.add_goldens([
    Golden(input="我的订单已经超过30天了，还能退款吗？",
           expected_output="非常抱歉，根据退款政策，超过30天的订单无法申请退款。如有特殊情况可联系人工客服。"),
    Golden(input="退款",   # 模糊输入
           expected_output="您好，请问您需要申请退款吗？能告诉我您的订单号吗？"),
])
dataset.push(alias="客服 Agent 测试集 v2")
```

**不想用云平台**：数据集用 JSONL 存 Git 仓库，用 Git tag 做版本。这个方案对国内团队更实际，也更符合你熟悉的工程习惯。

## 5.8 质量比数量重要

> **100 个精心设计的用例，比 1000 个随机生成的有价值得多。**

**判断一条用例是否有价值，看三点**：

| 检查项 | 说明 |
| --- | --- |
| 覆盖了真实失败场景吗 | Agent 从来不会在这条上失败 → 价值很低 |
| 有明确的 `expected_output` 吗 | 没有参考答案 → 只能靠 LLM 判断 → 可信度下降 |
| 覆盖边缘情况了吗 | 正常场景 Agent 一般都能处理 |

**硬性建议**：**数据集里至少 30% 是边缘情况和失败场景。**

**边缘情况清单**（照着构造，一条不落）：

| 类别 | 具体用例 |
| --- | --- |
| 工具层 | 返回空 `[]` / 返回 `null` / 超时 / 报错 / 返回超大结果 / 返回格式异常 |
| 输入层 | 空输入 / 超长输入 / 纯符号 / 乱码 / 多语言混杂 / emoji |
| 意图层 | 多意图 / 模糊意图 / 无关话题 / 意图中途变更 |
| 对话层 | 指代不明 / 话题跳转 / 前后矛盾 / 超长对话 |
| 安全层 | 提示注入 / 越狱 / 诱导泄露 / 诱导危险操作 |
| 业务层 | 权限不足 / 数据不存在 / 状态不允许 / 边界值（第 30 天 vs 第 31 天） |
| 时间层 | "上个月" / "明天" / 跨年 / 时区 |

> 这张表其实就是你做传统测试时的**异常场景清单**，只是加了 Agent 特有的意图层、对话层、安全层。**你的用例设计经验在这里 100% 复用。**

## 5.9 黄金数据集（Golden Dataset）的建设

黄金数据集 = 经过严格标注、可以作为基准的高质量数据集。

**准入标准**（一条样本要进黄金集，必须满足）：
1. 输入来自真实场景（生产日志或专家构造）
2. `expected_output` 经过 **2 人以上**独立标注且一致
3. 有明确的判定依据（不是"感觉不错"）
4. 有 `expected_trace` 或至少有工具调用的期望
5. 标注了难度、类别、来源

**用 Agent 辅助标注（阿里国际做法）**：
> 大部分判断很难写成简单规则，比如"文档是否完备""用户引导是否充足"。但它也不是完全主观。
> 把**评分维度、输入材料、输出格式和准出校验**写进 Skill，让 Agent 按固定顺序检查。
> 数据打分就从"专家凭感觉扫一眼"变成"**Agent 先按 SOP 过一遍，低分和异常样本再交给人看**"。
> 人不再被迫从零读所有材料，而是把注意力放在 Agent 标出来的矛盾点和低置信判断上。

**这个"人机协同标注"模式，是你未来平台里非常值得实现的功能。**

## 5.10 数据集运营（长期）

| 频率 | 动作 |
| --- | --- |
| 每周 | 从生产日志筛 10–20 条低分用例，人工标注入库 |
| 每两周 | 检查数据集分布（各难度/类别占比是否失衡） |
| 每月 | 检查饱和度；通过率 >95% 就补充难题 |
| 每季度 | 全量复审，剔除失效用例（业务已下线、知识已过期） |
| 每次线上事故 | **必须**转成用例入回归集（这是铁律） |

**数据集健康度看板指标**：
- 总量、各层占比（L1/L2/L3）
- 边缘用例占比（目标 ≥30%）
- 生产来源占比（目标 ≥40%，越高越贴近真实）
- 有 `expected_output` 的占比（目标 ≥80%）
- 最近 30 天新增数
- 各用例的"最后一次失败时间"（长期不失败的用例是候选淘汰对象）

## 5.11 标注规范细则与防污染

5.5 给了一条用例的"长什么样"，这一节把**每个字段怎么填、填错会怎样、怎么防止污染**讲细。这是数据集能长期保值的关键——否则 1000 条用例也是一笔糊涂账。

### 5.11.1 逐字段填写规则

| 字段 | 必填 | 取值 / 规则 | 填错的反例 |
| --- | --- | --- | --- |
| `id` | ✅ | 全局唯一，含类别+序号，如 `KQA-NEG-004` | `test1`（无类别、不可追溯） |
| `scene_code` | ✅ | 场景枚举，如 `knowledge_qa_negative` | 随手写 `test` |
| `category` | ✅ | `regression` / `capability` / `adversarial` | 留空（统计不了分布） |
| `input` | ✅ | 真实用户式输入，含边缘表达 | "请测试一下"（无具体任务） |
| `conversation_chain` | 多轮时 | 轮次列表；单轮填 `null` | 多轮任务却填 `null` |
| `expected_skill` | 视情况 | 期望命中的技能名 | 不填导致无法判路由 |
| `expected_route` / `expected_tools` | 视情况 | 有序步骤名 / 工具名集合；不约束则 `null` | 把"期望路径"和"实际路径"搞反 |
| `reference_output` | 黄金集必填 | 人工写的参考答案 | 用 LLM 随手生成不审（见防污染①） |
| `assertions` | ✅ | `must_contain` / `must_not_contain` / `must_not_fabricate` | 只写正向断言（负向才有杀伤力） |
| `eval_mode` | ✅ | `E2E_MOCK` / `E2E_REAL` | 该用 Mock 却用 Real（CI 不可复现） |
| `mock_data_id` | Mock 时 | 关联的 Mock 数据标识 | 引用的 Mock 不存在 |
| `reference_trace` | 工具类必填 | 期望的工具调用序列（含空结果标记） | 只写输出不写调用，无法判工具 |
| `difficulty` | ✅ | `easy`/`medium`/`hard` | 全填 `medium`（分层统计失效） |
| `source` | ✅ | `production_log` / `expert` / `synthetic` | 合成数据冒充生产数据 |
| `created_at` / `owner` / `notes` | ✅ | 责任人 + 备注 | 无 owner（出事找不到人） |

### 5.11.2 逐字段解读一个真实样例

拿 5.5 的 `KQA-NEG-004` 拆开看每个字段为什么这么填：

```json
{
  "id": "KQA-NEG-004",                 // 类别(NEG=负例) + 序号，一眼知道是"知识库负例第4条"
  "scene_code": "knowledge_qa_negative",
  "category": "adversarial",           // 故意问不存在的接口 → 对抗/边界类
  "input": "IC 服务的 batchQueryProductDetail 接口限流是多少？",
  "expected_skill": "KnowledgeQA",
  "expected_route": "SKILL_MISS",      // 关键：知识库根本没这接口 → 期望"未命中"
  "expected_tools": [{"name": "repo_vector_search"}],
  "reference_output": "抱歉，我在知识库中没有找到…建议您联系 IC 服务负责人确认。",
  "assertions": {
    "must_contain": ["没有找到", "建议"],   // 正向：必须承认"不知道"
    "must_not_contain": ["QPS", "限流为", "每秒"],  // 负向：绝不能编造具体数值
    "must_not_fabricate": true                  // 触发 Faithfulness 判定
  },
  "reference_trace": [{"tool":"repo_vector_search","result_empty": true}],  // 工具返回空 → Agent 应如实说"没找到"
  "difficulty": "hard",
  "source": "production_log",          // 真实日志来的 → 价值最高
  "owner": "张三"
}
```

**为什么这条例子"值钱"**：它同时用了三层防护——`expected_route=SKILL_MISS`（路由层）、`must_not_contain`（输出层负向断言）、`must_not_fabricate`（忠实度层）。任何一层失效都能被抓住，这就是 5.8 说的"边缘情况 + 负向断言比正向更有杀伤力"。

### 5.11.3 防污染 / 防泄露 6 条（数据集的生死线）

> 数据集一污染，所有指标都变成"自欺欺人"。这 6 条直接决定评测可信度。

1. **生成 `reference_output` 的模型 ≠ 被测 Agent 模型**
   用同一个模型生成答案又去评它，分数会虚高（两者"思路一致"）。务必换厂商模型生成，或人工写。
2. **用例不得与训练/微调语料重叠**
   自有模型尤其注意：评测集若曾进过训练集，等于"开卷考试"。定期做去重比对。
3. **生产日志入仓前必须脱敏**
   PII（手机号、订单号、地址）先去标识再入库，否则数据集本身就成了泄露源。
4. **黄金集需 2 人以上独立标注且一致**
   单人标注的主观偏差会被当成"标准"。分歧大说明判定依据本身模糊，先统一口径（对齐 4.2 的 Kappa ≥ 0.6）。
5. **难度 / 类别分布必须可查**
   全填 `hard` 或全 `easy` 都会让"总分"失真。用 5.10 的健康度看板盯住分布。
6. **对抗样本不要"写死答案"**
   测的是 Agent **行为**（是否拒绝、是否编造），不是"输出里有没有某个关键词"。写死关键词的对抗样本，Agent 换个说法就绕过了。

### 5.11.4 黄金集准入 5 问 checklist

一条候选用例，挨个回答，全"是"才进黄金集：

- [ ] 输入来自真实场景（生产日志或专家构造）？
- [ ] `reference_output` 经过 **2 人独立标注且一致**？
- [ ] 有明确的判定依据（不是"感觉不错"）？
- [ ] 标了难度、类别、来源，能进健康度统计？
- [ ] 覆盖了边缘 / 失败场景（不是"正常也能过"的题）？

> 这 5 问和 3.8 的指标定义表、4.9 的 Judge 校准是一套逻辑：**指标、用例、评分器，三者都要"可被追问"**。任何一个环节讲不清，整套评测的可信度就塌了。
