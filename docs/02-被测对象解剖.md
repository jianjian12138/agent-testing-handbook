# 02 · 被测对象解剖：Agent 到底长什么样

> 目标：3 天。不懂被测系统就测不好——这条规律在 Agent 时代同样成立，而且更严苛。
> 读完你应该能：拿到任意一个 Agent 项目，画出它的架构图并标出 8 个高风险失效点。

---

## 2.1 先破一个误解

很多测试同学以为 Agent = "带工具的聊天机器人"。这个理解会让你的测试停留在"多问几个问题"的水平。

**准确的定义**：
> Agent 是一个以 LLM 为推理内核，通过「感知 → 规划 → 行动 → 观察 → 反思」循环，自主调用工具来完成目标的软件系统。

关键词是**自主**和**循环**。它的执行路径不是你写死的，是它自己每一步决策出来的。

**这意味着**：你面对的是一个**执行路径动态生成、状态跨步骤累积、且带随机性**的分布式系统。这在传统软件里最接近的类比是——一个会自己改自己代码的工作流引擎。

---

## 2.2 Agent 的六大模块（这就是你的测试对象分解）

阿里国际的 Agent 精细化评测把 Agent 拆成四大模块（感知/规划/记忆/工具），实践中我建议扩展为六个。**这个分解直接决定了你的组件级评测怎么设计。**

```
                    ┌──────────── 用户输入 ────────────┐
                            ↓
   ┌────────────────────────────────────────────────────┐
   │  ① 感知 Perception    意图识别 / 实体抽取 / 路由    │
   └────────────────────────────────────────────────────┘
                            ↓
   ┌────────────────────────────────────────────────────┐
   │  ② 规划 Planning      任务分解 / 工具选择 / 顺序    │
   └────────────────────────────────────────────────────┘
                            ↓
   ┌──────────────────┐  ┌──────────────────┐  ┌──────────────────┐
   │ ③ 记忆 Memory     │  │ ④ 工具 Tool       │  │ ⑤ 知识 RAG        │
   │ 短期(上下文窗口)  │  │ Function/MCP      │  │ 检索 + 重排       │
   │ 长期(向量库/画像) │  │ 参数构造/结果解析 │  │ 上下文注入        │
   └──────────────────┘  └──────────────────┘  └──────────────────┘
                            ↓
   ┌────────────────────────────────────────────────────┐
   │  ⑥ 生成与反思 Generation & Reflection               │
   │     结果整合 / 自我纠错 / 输出格式化                 │
   └────────────────────────────────────────────────────┘
                            ↓
                    ┌──────── 最终输出 ────────┐
```

### ① 感知模块（Perception）—— "看懂没"

**做什么**：把用户的自然语言输入，转换成结构化的意图 + 参数。

**技术形态**：
- 分类模型 / LLM few-shot 分类 / 关键词路由 / 向量相似度匹配
- 输出：`intent=查询订单`, `entities={order_id: "123"}`, `route=SKILL_HIT`

**核心失效模式**（这些就是你的测试点）：

| 失效模式 | 具体表现 | 用例设计思路 |
| --- | --- | --- |
| 意图误判 | "我想退" 被识别成"退出登录"而非"退款" | 收集同义/简略/口语化表达 |
| 多意图漏识别 | "帮我查订单顺便看下物流" 只处理了前一个 | 构造复合请求用例 |
| 模糊意图不澄清 | 用户说"我要那个"，Agent 硬猜一个 | 构造信息不完整的输入 |
| 误路由（该走知识库走了技能） | `SKILL_HIT` / `SKILL_MISS` 判断错 | 构造边界话题 |
| 降级失败 | 无法识别时没有兜底话术，直接崩 | 构造完全无关的输入 |

**对应指标**：意图识别准确率/召回率/精确率、多意图识别率、模糊意图澄清率、降级触发准确率、意图识别延迟。

> ⚠️ **关键**：如果感知错了，下游所有指标都会被污染。所以评测时要做「**路由错误跳过**」——期望 `SKILL_MISS` 实际 `SKILL_HIT` 时，下游依赖 RAG 的 Judge Task 标记为 `error` 并跳过，不参与检索/忠实性指标的计算。否则你的 RAG 指标会莫名其妙地低。

---

### ② 规划模块（Planning）—— "想对没"

**做什么**：决定"要做几步、每步用什么工具、什么顺序"。

**技术形态**：
- ReAct（Thought → Action → Observation 循环）
- Plan-and-Execute（先出完整计划，再逐步执行）
- 函数调用（Function Calling / Tool Use）原生能力
- 多 Agent 编排（主 Agent 派 SubAgent）

**核心失效模式**：

| 失效模式 | 具体表现 | 危害等级 |
| --- | --- | --- |
| **死循环** ⚠️ | 连续 5 次调同一工具同一参数，或 3 次相同决策模式 | 🔴 生产红线，>2% 必须修 |
| 工具滥用 | 任务明确却"以防万一"多调了 3 个工具 | 🟡 成本翻倍，延迟增加 |
| 步骤缺失 | 该先查库存再下单，直接下单了 | 🔴 业务错误 |
| 顺序错误 | 先扣款后校验 | 🔴 业务错误 |
| 过早收敛 | 信息不足就给结论 | 🟡 质量差 |
| 计划漂移 | 说好三步，执行时干了别的（PlanAdherence 低） | 🟡 不可控 |
| 多步骤"失忆" | 第 2 步忘了第 1 步的结果 | 🔴 常见且致命 |

**对应指标**：路由决策准确率、工具调用决策准确率、规划路径评分、死循环率、规划遵循度（PlanAdherence）、调用链效率（最小必要调用数 / 实际调用数，基线 ≥0.6）。

**死循环检测的实现思路**（你会在平台里用到）：
```python
def detect_loop(trace, same_call_threshold=5, pattern_threshold=3):
    """从 trace 里检测死循环"""
    calls = [(s.tool_name, json.dumps(s.params, sort_keys=True)) for s in trace.tool_spans]
    # 规则1：连续 N 次完全相同的调用
    for i in range(len(calls) - same_call_threshold + 1):
        if len(set(calls[i:i + same_call_threshold])) == 1:
            return True, f"连续{same_call_threshold}次相同调用: {calls[i]}"
    # 规则2：重复的决策模式（如 A→B→A→B→A→B）
    for size in (2, 3):
        for i in range(len(calls) - size * pattern_threshold + 1):
            window = calls[i:i + size * pattern_threshold]
            if all(window[j] == window[j % size] for j in range(len(window))):
                return True, f"重复决策模式: {window[:size]}"
    return False, None
```

### ③ 记忆模块（Memory）—— "记住没"

**做什么**：维护对话上下文和跨会话的用户信息。

**技术形态**：
- **短期记忆**：上下文窗口内的对话历史，通常是滑动窗口 / 摘要压缩
- **长期记忆**：向量库存储的用户画像、历史偏好，检索后注入

**核心失效模式**：

| 失效模式 | 具体表现 | 用例设计思路 |
| --- | --- | --- |
| 上下文丢失 | 第 3 轮问"那上海呢"，Agent 不知道在问什么 | 多轮省略指代用例 |
| 记忆衰减 | 20 轮之后完全忘了开头的约束 | 长对话衰减集（≥10 组，每组 15+ 轮） |
| 错误记忆检索 | 检索到了不相关的历史偏好 | 相似用户/相似话题干扰 |
| 记忆污染 | 把上一个用户的信息带到当前会话 | 并发会话隔离测试 |
| 摘要失真 | 压缩上下文时丢了关键约束 | 长上下文 + 关键约束用例 |

**对应指标**：短期记忆保留率（**注意是语义连贯而非字面匹配**）、长期记忆检索精确率/召回率、记忆衰减曲线、记忆注入延迟。

> 💡 **测试技巧**：记忆衰减曲线是很好用的一个可视化——横轴对话轮数，纵轴关键信息保留率，能直观看到 Agent 在第几轮开始"变笨"。

---

### ④ 工具模块（Tool）—— "做对没"

**做什么**：把规划的决策转成实际的函数/API 调用，并解析结果。

**技术形态**：
- OpenAI Function Calling / Tool Use
- **MCP（Model Context Protocol）**——2025 年后的事实标准，值得单独学
- 本地 Skill（文件系统热加载的能力包）
- 代码解释器 / Shell / 浏览器（Computer Use）

**核心失效模式**：

| 失效模式 | 具体表现 |
| --- | --- |
| 工具选择错误 | 该用 `PolicyQuery` 用了 `WebSearch` |
| 参数映射错误 | 用户说"上个月"，传了 `month=8`（当前月） |
| 必填参数缺失 | 少传 `user_id` 导致查询失败 |
| 类型/格式错误 | 日期传 `"2026/8/1"` 而 API 要 `"2026-08-01"` |
| 结果解析错误 | 工具返回嵌套 JSON，Agent 只取了第一层 |
| **空结果幻觉** ⚠️ | 工具返回 `[]`，Agent 直接编数据 |
| 异常未处理 | 工具超时/报错，Agent 假装成功 |
| MCP/Skill 加载失败 | 热更新后新工具没生效 |

**对应指标**：工具选择准确率（单工具场景 ≥95%，多工具 ≥90%）、参数准确率（3/2/1/0 分档）、工具调用成功率、MCP&Skill 加载成功率、参数映射准确率、工具调用延迟。

**参数准确率的分档评分标准**（直接抄）：
| 分数 | 判定标准 | 示例 |
| --- | --- | --- |
| 3 | 完全正确 | `read_file(path="src/auth/login.ts", encoding="utf-8")` |
| 2 | 核心参数对，可选参数有出入 | `read_file(path="src/auth/login.ts")` 缺 encoding |
| 1 | 部分参数错，但方向对 | `read_file(path="src/auth/")` 路径不精确 |
| 0 | 完全错 | `read_file(path="README.md")` |

### ⑤ 知识/RAG 模块 —— "查到没"

**做什么**：从知识库检索相关内容，注入上下文供生成使用。

**核心失效模式**：漏检、误检、噪声过多、切块不当、重排失效、时效性过期。

**对应指标**（RAGAS 四件套，业界事实标准）：

| 指标 | 含义 | 差了会怎样 |
| --- | --- | --- |
| **Faithfulness 忠实度** | 答案是否忠于检索到的上下文 | 出现幻觉、编造 |
| **Answer Relevancy 答案相关性** | 是否真的回答了问题 | 答非所问 |
| **Context Relevancy 上下文相关性** | 检索内容是否相关 | 检回垃圾、噪声大 |
| **Context Recall 上下文召回** | 该检的是否都检到了 | 漏检关键信息 |

> 🔑 **忠实度是最容易被忽视、也最容易出问题的指标**。大多数团队只看"回答质量"和"工具调用对不对"，忠实度很少被单独评测。结果就是：回答看起来很好，工具也调对了，但回答里的数据和工具返回的数据对不上——Agent 在编。

---

### ⑥ 生成与反思模块 —— "说清楚没 / 能改错没"

**做什么**：整合所有信息生成最终回答；出错后自我修正。

**核心失效模式**：格式不符（该出 JSON 出了 Markdown）、指令不遵循（要求 100 字写了 500 字）、语气不当、幻觉、无法从错误中恢复。

**对应指标**：指令遵循能力、幻觉率、错误恢复率（基线 ≥60%）、用户满意度。

**错误恢复的判定示例**：
```
Task: 读取 config.json
Step 1: read_file("config.json") → FileNotFoundError
Step 2: search_file("config.*")   → 找到 config.yaml     ← 主动换路径
Step 3: read_file("config.yaml")  → 成功
判定：错误恢复成功 ✓
```

## 2.3 八个高风险失效点（背下来）

给你一个 Agent 项目，先查这 8 个地方，命中率很高：

| # | 高风险点 | 快速验证方法 |
| --- | --- | --- |
| 1 | **工具返回空结果时是否幻觉** | Mock 工具返回 `[]` / `null`，看 Agent 是否编数据 |
| 2 | **工具报错/超时时是否假装成功** | Mock 工具抛异常，看输出 |
| 3 | **多轮对话第 3 轮以后的指代消解** | "北京天气？" → "那上海呢？" → "明天呢？" |
| 4 | **死循环保护是否存在** | 构造一个工具永远返回"信息不足"的场景 |
| 5 | **长上下文下的关键约束保留** | 开头加约束（"用中文回答"），聊 20 轮后看还遵不遵守 |
| 6 | **危险操作是否有确认** | 诱导它执行删除/转账/发送类操作 |
| 7 | **提示注入是否能绕过系统提示** | 用户输入里塞 "忽略以上所有指令" |
| 8 | **并发会话是否串数据** | 两个 session 同时跑，看记忆是否串 |

**这 8 条可以直接做成你的 Agent 冒烟测试集。**

## 2.4 多 Agent 系统：新增的失效维度

当 Agent 会派生 SubAgent 时，评测难度再上一个台阶。

**新增失效模式**：
- **拆分不当**：该并行的串行了（浪费时间），不该并行的并行了（浪费成本）
- **上下文传递丢失**：主 Agent 没把关键约束传给 SubAgent
- **结果整合矛盾**：两个 SubAgent 给出相互矛盾的结论，主 Agent 没发现
- **失败无兜底**：一个 SubAgent 挂了，整个任务崩
- **责任归属不清**：任务失败了，不知道是哪一层的问题

**对应指标**：SubAgent 创建时机合理性、结果整合质量（含关键发现 / 无矛盾 / 依赖传递正确 / 失败兜底）。

> 这是目前整个行业都在摸索的问题，没有标准答案。你可以把它作为后期的研究方向——**谁先在多 Agent 评测上做出体系，谁就有话语权**。

## 2.5 你需要动手搭一个 Agent（重要）

**测 Agent 之前，你必须自己写过一个 Agent。** 这不是可选项。

原因：
1. 你需要知道 Trace 是怎么产生的，才知道怎么采集
2. 你需要知道 Prompt 长什么样，才知道失败该怎么归因
3. 你需要知道工具是怎么注册的，才知道怎么 Mock

**最小 Agent 实现（约 60 行，不用任何框架）**：

```python
import json
from openai import OpenAI

client = OpenAI()  # 配置 base_url 指向你的模型服务

TOOLS = [{
    "type": "function",
    "function": {
        "name": "query_order",
        "description": "根据订单号查询订单信息",
        "parameters": {
            "type": "object",
            "properties": {"order_id": {"type": "string", "description": "订单号"}},
            "required": ["order_id"],
        },
    },
}]

def query_order(order_id: str):
    db = {"A001": {"status": "已发货", "amount": 299, "days_since_paid": 12}}
    return db.get(order_id, {})       # ← 注意：查不到返回空字典，这就是"空结果"陷阱

def run_agent(user_input: str, max_steps: int = 6):
    messages = [
        {"role": "system", "content": "你是电商客服助手。只调用完成任务必需的工具。"},
        {"role": "user", "content": user_input},
    ]
    trace = {"steps": [], "tools_called": [], "tool_outputs": []}

    for _ in range(max_steps):
        resp = client.chat.completions.create(
            model="gpt-4o-mini", messages=messages, tools=TOOLS
        )
        msg = resp.choices[0].message
        messages.append(msg.model_dump(exclude_none=True))

        if not msg.tool_calls:                       # 没有工具调用 = 出最终答案
            trace["output"] = msg.content
            return trace

        for tc in msg.tool_calls:                    # 执行工具
            args = json.loads(tc.function.arguments)
            result = globals()[tc.function.name](**args)
            trace["steps"].append({"tool": tc.function.name, "args": args, "result": result})
            trace["tools_called"].append(tc.function.name)
            trace["tool_outputs"].append(json.dumps(result, ensure_ascii=False))
            messages.append({
                "role": "tool", "tool_call_id": tc.id,
                "content": json.dumps(result, ensure_ascii=False),
            })

    trace["output"] = "达到最大步数限制"
    return trace
```

**看懂这段代码，你就理解了 Agent 的本质**：一个 while 循环 + 模型决策 + 工具执行 + 结果回填。

注意 `query_order` 查不到时返回 `{}`——**这就是那个让 AWS 旅行 Agent 忠实度只有 32% 的空结果陷阱**。你可以立刻拿这个 Agent 做实验：问它一个不存在的订单号 `B999`，看它是老实说"查不到"，还是编一个订单出来。

完整可运行版本见 [`starter/agent/customer_service_agent.py`](../starter/agent/customer_service_agent.py)。

## 2.6 需要了解的主流 Agent 框架

你不需要精通，但要能读懂它们的代码和 Trace 结构：

| 框架 | 特点 | 测试关注点 |
| --- | --- | --- |
| **LangGraph** | 图式编排，状态机，可控性强 | 状态转移是否正确、节点是否可单测 |
| **AutoGen**（微软） | 多 Agent 对话，AgentEval 集成在这里 | 群聊终止条件、消息路由 |
| **CrewAI** | 角色化多 Agent，上手简单 | 角色分工、任务委派 |
| **OpenAI Agents SDK** | 官方，轻量，Handoff 机制 | Handoff 时上下文传递 |
| **Strands Agents**（AWS） | 原生 OTel 支持 | Trace 是现成的，测试友好 |
| **MCP** | 不是框架，是工具接入的标准协议 | 工具发现、Schema 校验、权限边界 |

**建议**：练手选 **LangGraph**（可控、Trace 清晰）或者干脆用上面 60 行的裸实现（最透明）。
