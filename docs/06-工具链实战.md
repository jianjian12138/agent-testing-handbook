## 6.1 工具链全景：一张图看清分工

```
                 ┌───────────────── 离线评测（Offline / 评测集） ─────────────────┐
                 │                                                          │
   数据集 ──►  Agent  ──►  轨迹(Trace)  ──►  Grader  ──►  分数 + 报告
                 │                    │                │
            [被测对象]          [DeepEval /     [promptfoo /
                                 RAGAS /        Inspect AI /
                                 自写代码]       AgentEval]
                 │                    │                │
                 └────────────────────┼────────────────┘
                                      ▼
                          ┌── 结果存储 & 看板 ──┐
                          │  Langfuse / Opik     │
                          │  (实验追踪 + 对比)   │
                          └─────────────────────┘

                 ┌───────────────── 在线可观测（Online / 生产） ─────────────────┐
   用户请求 ──► Agent ──► OTel Span ──► Langfuse/Opik ──► 在线评分器 ──► 告警/回流
```

**一句话分工**：

| 工具 | 角色 | 类比传统自动化 |
| --- | --- | --- |
| **DeepEval** | 离线评测引擎（pytest 风格） | pytest + 断言库 |
| **promptfoo** | 红蓝对抗 / 多模型 / 提示词对比 | 参数化测试 + 对比报告 |
| **RAGAS** | RAG 专项指标（忠实度等） | 专项断言插件 |
| **Inspect AI** | 研究型 benchmark 评测框架 | JUnit + 报告 |
| **Langfuse / Opik** | 轨迹追踪 + 实验管理 | Allure + 测试管理 |
| **Giskard** | 鲁棒性 / 对抗扫描 | 模糊测试(fuzzing) |
| **AWS Agent-EvalKit** | 旅行/客服类 Agent 端到端评测 | 端到端测试套件 |

> 你作为传统测试出身，**DeepEval + Langfuse** 是首选组合：一个管"怎么跑、怎么断言"，一个管"跑完去哪看、怎么对比"。其余按需补。

## 6.2 DeepEval：你的主力评测引擎

DeepEval 用 pytest 的写法描述"评测用例"，用 **Metric（指标）** 代替 assert。它的核心价值是：**把文档 03 的指标体系直接落成可执行代码**。

### 6.2.1 最小可跑示例（对应 P3 项目）

```python
# evals/test_p3_tool_correctness.py
import pytest
from deepeval import assert_test
from deepeval.metrics import ToolCorrectnessMetric
from deepeval.test_case import (
    AgentTestCase,
    ToolCall,
)

def test_query_order_called():
    # 输入：用户问"我的订单到哪了"
    input = "我的订单到哪了？"

    # 实际 Agent 跑出来的工具调用（这里用真实 Agent 的输出）
    actual_tools = [
        ToolCall(name="query_order", args='{"order_id": "12345"}')
    ]

    # 期望的工具调用（来自数据集 05 的 expected_trace）
    expected_tools = [
        ToolCall(name="query_order", args='{"order_id": "12345"}')
    ]

    test_case = AgentTestCase(
        input=input,
        actual_output="已帮您查询订单 12345，正在配送中。",
        tools_called=actual_tools,
        expected_tools=expected_tools,
    )

    metric = ToolCorrectnessMetric(threshold=0.8)
    assert_test(test_case, [metric])
```

跑：`deepeval test run evals/test_p3_tool_correctness.py`（或直接 `pytest`）。失败时 DeepEval 会给出每个 metric 的得分和原因——这就是"评测报告"。

### 6.2.2 Agent 测试三大专属 Metric

| Metric | 测什么（文档 03 对应指标） | 关键参数 |
| --- | --- | --- |
| `ToolCorrectnessMetric` | 工具质量（是否调对、调全） | `expected_tools` 必填 |
| `PlanAdherenceMetric` | 规划推理（是否按既定计划走） | 需 LLM 判定计划一致性 |
| `AgentGoalCompletionMetric` | 任务完成度（最终是否达成目标） | 用 LLM-as-Judge 判完成 |

> ⚠️ 这三个 Metric 默认依赖 LLM 作为判别器（即 LLM-as-Judge，见文档 04）。这意味着**评测本身也有非确定性**——务必配合文档 01 的 `pass@k` 多跑取稳。

### 6.2.3 非确定性下的稳定跑法

```python
# evals/run_trials.py  —— 取自文档 04 的执行引擎思路
import subprocess, statistics

def run_trials(file: str, k: int = 5):
    scores = []
    for i in range(k):
        r = subprocess.run(
            ["deepeval", "test", "run", file],
            capture_output=True, text=True
        )
        # 解析 DeepEval 输出的平均得分
        score = parse_score(r.stdout)
        scores.append(score)
    return {
        "pass@k": any(s >= 0.8 for s in scores),  # 至少一次达标
        "pass^k": all(s >= 0.8 for s in scores),  # 全部达标
        "mean": statistics.mean(scores),
        "min": min(scores), "max": max(scores),
    }
```

## 6.3 promptfoo：红蓝对抗 & 多版本对比

promptfoo 强在**把一个 Agent/提示词跑多遍、对多个模型、用多个测试用例横向对比**，输出 HTML 对比报告。特别适合：

- 提示词 A/B 测试（"加 CoT 后 Judge 一致率是否上升"）
- 对抗注入扫描（"用户说'忽略之前指令'时 Agent 是否失守"）
- 回归门禁（CI 里对比 master 与新分支的得分）

```yaml
# promptfooconfig.yaml
providers:
  - openai:gpt-4o
  - anthropic:claude-sonnet-4
tests:
  - vars:
      user_input: "我的订单到哪了？"
    assert:
      - type: llm-rubric
        value: "必须调用 query_order 工具，且不得编造订单状态"
      - type: contains-json  # 结构化输出校验
```

跑：`promptfoo eval`，看 `promptfoo view` 的对比矩阵。

## 6.4 RAGAS：RAG 类 Agent 的专项体检

如果你的 Agent 带知识库（RAG），RAGAS 四件套是必做项（详见文档 03）：

- **Faithfulness（忠实度）**：回答是否都来自检索到的上下文，**不臆造**。这是最易被忽视也最致命的指标。
- **Answer Relevancy（答案相关性）**：答非所问？
- **Context Relevancy / Context Recall**：检索到的上下文是否相关、是否漏检。

```python
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy

results = evaluate(
    dataset=rag_dataset,           # 含 question / contexts / answer
    metrics=[faithfulness, answer_relevancy],
)
print(results)
```

## 6.5 Langfuse / Opik：轨迹追踪与实验管理

这两个是"评测界的 Allure + 测试管理"，但更强——它们能**回放每一次 Agent 调用的完整思维链**。

核心价值（对你这种要做平台的人尤其重要）：

1. **Trace 可视化**：每一步 LLM 调用、工具调用、耗时、token 成本一目了然。
2. **实验对比**：同一数据集跑两版 Agent，得分曲线并排看。
3. **数据集管理**：直接在 UI 里维护评测集、标 Golden。
4. **在线评分**：生产流量回流后自动跑评分器，触发告警。

```python
# 给 Agent 套一层 Langfuse 追踪（OpenTelemetry 兼容）
from langfuse.decorators import observe, langfuse_context

@observe()
def agent_step(prompt):
    return llm_call(prompt)

# 之后在 Langfuse UI 就能看到完整调用树 + 每个 step 的成本
```

> 平台搭建（文档 09）的"可观测层"就基于这套。现在先把它当"高级 Allure"用起来。

## 6.6 Giskard & Inspect AI & AWS Agent-EvalKit：按需补位

| 工具 | 何时用 |
| --- | --- |
| **Giskard** | 想做鲁棒性扫描 / 对抗样本自动生成（类似模糊测试）时用 |
| **Inspect AI** | 做学术研究型 benchmark、需要严格可复现评分时用 |
| **AWS Agent-EvalKit** | 做客服/旅行/预订类端到端 Agent，直接复用其六阶段工作流（plan/data/trace/run_agent/eval/report） |

## 6.7 选型决策树（直接照着选）

```
你的 Agent 是什么类型？
├─ 纯工具调用 / 任务型 ──► DeepEval（ToolCorrectness + GoalCompletion）
│                         + Langfuse（看板）
├─ 带知识库 RAG ─────────► DeepEval + RAGAS（忠实度必测）
├─ 多 Agent 协作 ────────► DeepEval + 自写代码评分器（文档 04 Agent-as-Judge）
├─ 要做对抗/合规扫描 ───► promptfoo + Giskard
└─ 研究 benchmark ──────► Inspect AI / AWS Agent-EvalKit
```

**工具链落地的三个铁律**：
1. 先用 DeepEval 把 1 条用例跑通，再谈扩展——别一上来搭大而全。
2. 一切指标必须能进 CI（文档 08 的 P3 质量门禁）。
3. 评测结果必须有去处（Langfuse/Opik），否则等于白跑。
