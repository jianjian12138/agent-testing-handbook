# 09 · 平台搭建：你的 Agent 测试自动化平台

> 目标：贯穿阶段四，作为转型的最终作品。
> 你说过："自动化测试我可以搭建自动化测试平台，Agent 测试也希望可以搭建自己的 Agent 测试自动化平台。"
> 这一篇就是为你定制的——把前面所有方法论，落成**一个你能自己搭的平台**。

---

## 9.1 平台定位：不是"再写一个 DeepEval"

先划清边界，避免你掉进"重复造轮子"的坑：

```
┌─────────────── 你不用造（直接用） ───────────────┐
│ DeepEval / promptfoo / RAGAS / Langfuse / OTel   │
└──────────────────────────────────────────────────┘
                    ▲ 你在其上搭
┌─────────────── 你要造的（平台） ─────────────────┐
│ 数据集管理 · 评测编排 · 质量门禁 · 看板 · 回流   │
└──────────────────────────────────────────────────┘
```

**平台的核心价值 = 把"评测"变成"团队任何人点一下就能跑的服务"**，而不是你一个人写脚本。

---

## 9.2 平台总体架构

```
┌─────────────────────────────────────────────────────────────┐
│                        用户入口层                              │
│   Web UI / CLI  │  数据集上传  │  一键评测  │  报告查看        │
└───────────────┬─────────────────────────────────┬───────────┘
                │                                   │
┌───────────────▼──────────┐      ┌─────────────────▼──────────┐
│      数据集管理层          │      │        评测编排层            │
│ · 数据集 CRUD             │      │ · 任务调度(并行/重试)        │
│ · 版本管理                │      │ · E2E_MOCK / E2E_REAL 双模  │
│ · 标注(人工/AI)           │      │ · 多模型/多Agent 支持        │
│ · 黄金集准入              │      │ · pass@k 多次采样            │
└───────────────┬──────────┘      └─────────────────┬──────────┘
                │                                   │
┌───────────────▼──────────┐      ┌─────────────────▼──────────┐
│      评分器层(Grader)      │      │      质量门禁(Quality Gate) │
│ · 代码评分器              │◄────►│ · 核心指标阻断合并          │
│ · LLM-as-Judge           │      │ · 辅助指标告警              │
│ · Agent-as-Judge         │      │ · L1/L2/L3 分级            │
│ · 人工评分                │      │                            │
└───────────────┬──────────┘      └─────────────────┬──────────┘
                │                                   │
┌───────────────▼───────────────────────────────────▼──────────┐
│              存储 & 可观测层（Langfuse/Opik + OTel）            │
│   Trace 留存 · 实验对比 · 在线评分 · 失败回流 · 成本/性能基线    │
└─────────────────────────────────────────────────────────────┘
```

**五个层，对应你前面学过的五篇**：数据集(05) → 编排(06) → 评分(04) → 门禁(03) → 可观测(07)。

## 9.3 六里程碑演进路线（M1–M6）

不要一口吃成胖子。按下面节奏，每到一个里程碑都是可用状态：

### M1 · 本地评测脚本（第 6 周，对应 P3）
- 一个 `run_suite.py`，读数据集、跑 DeepEval、出报告
- **交付**：你本地能一键评测
- **验收**：`python run_suite.py` 出分数 + 失败列表

### M2 · 数据集可视化管理（第 7 周）
- 数据集从"文件夹里的 JSON"变成"有 schema、有版本、能增删"
- 加 `expected_trace` / `must_not_fabricate` 字段校验
- **交付**：数据集不再靠手改文件
- **验收**：上传一条样本，系统校验格式并去重

### M3 · CI 质量门禁（第 8 周，对应 P3 收尾）
- 评测接进 CI，核心指标阻断合并（文档 08 P3）
- **交付**：平台第一次"自动拦人"
- **验收**：故意改坏 Agent，PR 被拦

### M4 · 在线可观测 + 回流（第 9–10 周，对应 P4）✅ 已落地（本地骨架）
- `starter/platform/trace.py`：统一 Tracer + 三后端（Local/OTel/Langfuse），`traced_agent.py` 套埋点，`render_traces.py` 出瀑布图
- `starter/platform/feedback.py`：失败回流（未通过用例收进 `datasets/candidates/backlog.json`）
- **交付**：本地已能产出 Trace 并回流入候选集；接 Langfuse/OTel 只需设环境变量
- **验收**：`python demo_trace.py` 出 `traces_report.html`；`python feedback.py report_p2.json` 把 P2 失败用例收进候选集
- 进阶（接生产）：把 Local backend 切到 OTel/Langfuse，并把 `feedback.py` 接到在线评分器触发

### M5 · Web 平台化（第 11 周）✅ 已落地（零依赖骨架）
- `starter/platform/web.py`：**零依赖 `http.server` 仪表盘**，把 M1–M4 包成可点开看的 Web 平台
  - `GET /`：仪表盘（通过率、各维度柱状图、失败用例下钻）
  - `GET /api/report?path=...`：报告统计 JSON
  - `POST /api/eval/run`：服务端进程内跑 P2 评测（可选 agent / judge / trials），实时回显
  - `POST /api/dataset/upload`：上传/覆盖数据集
- 看板：总通过率、各维度通过率、边缘用例覆盖、失败下钻
- **交付**：同事能自己跑评测（无需装 Flask/FastAPI）
- **验收**：非测试同事上传数据集 + 点按钮出报告
- 进阶（接生产）：把 `http.server` 换成 FastAPI，前端接 Langfuse 自托管 + 自写编排服务，数据集落 Postgres/对象存储（见 9.4 选型）

### M6 · 多 Agent 评测 & 智能门禁（第 12 周，对应 P5）
- 支持多 Agent 协作评测（Agent-as-Judge）
- 门禁从"固定阈值"进化到"基于趋势的动态基线"
- **交付**：平台原型完整
- **验收**：新 Agent 接入 ≤ 10 分钟出"能不能发"结论

## 9.4 技术选型建议（给你搭平台用）

| 层 | 推荐 | 备注 |
| --- | --- | --- |
| 语言 | **Python** | 评测生态全在 Python |
| 评测引擎 | DeepEval + promptfoo | 不重复造 |
| 追踪/看板 | Langfuse（自托管） | OTel 原生、开源可私有部署 |
| 存储 | Postgres + 对象存储(数据集) | 数据集版本用对象存储 |
| 任务调度 | 本地线程池 → Celery/RQ | M1 用线程，M5 上升级 |
| 接口 | FastAPI | 轻、好测 |
| 前端 | 先 CLI，M5 再用 Streamlit/Gradio 快速出 UI | 别在 UI 上耗太久 |
| CI | GitHub Actions / GitLab CI | 门禁载体 |

> 你做传统测试平台时积累的工程能力（调度、存储、权限、报告）**直接复用**。Agent 测试平台 80% 是普通软件工程，只有 20% 是评测方法论——这 20% 前面 7 篇已经给你备好了。

---

## 9.5 平台搭建的五个坑（提前避）

1. **一上来就做 Web**：先 M1 脚本跑通，UI 是最后 20%。
2. **门禁阈值拍脑袋**：用文档 03 的 L1/L2/L3 + 生产基线定阈值，别凭感觉。
3. **忽视非确定性**：平台必须内置 `pass@k` 多次采样，单次评测不可信。
4. **只测离线不接生产**：没有在线评测 + 回流，数据集会长歪。
5. **重复造评测引擎**：DeepEval 等直接用，你的差异化在"编排 + 门禁 + 看板 + 回流"。

## 9.7 平台已落地交付物（M1–M5 总览）

| 里程碑 | 文件 | 跑通方式 |
| --- | --- | --- |
| M1 评测编排 | `starter/platform/run_suite.py` | `python run_suite.py --report report.json` |
| M3 质量门禁 | `starter/platform/quality_gate.py` | `python quality_gate.py report.json` |
| M4 可观测 | `starter/platform/trace.py` + `demo_trace.py` + `feedback.py` | `python demo_trace.py` → `traces_report.html` |
| M4+ P2 回流 | `starter/p2/`（`run_p2.py` 已接 M4 Tracer） | `python run_p2.py --report report_p2.json` |
| M5 Web 平台 | `starter/platform/web.py` | `python web.py` → 打开 http://127.0.0.1:8000 |

**端到端演示脚本（证明四里程碑串起来）**：
```bash
# 1) P2 用「含缺陷 Agent」跑 → 门禁阻断，并打出浏览器 Agent 的 Trace
cd starter/p2 && python run_p2.py --report report_p2.json
# 2) 同样的数据集换「正确 Agent」→ 100% 通过（证明门禁抓的是缺陷而非误杀）
python run_p2.py --agent realistic --report report_realistic.json
# 3) 失败用例回流入候选集（M4 闭环）
python ../platform/feedback.py report_p2.json
# 4) 打开 Web 看板（M5）回看任意报告
cd ../platform && python web.py
```
