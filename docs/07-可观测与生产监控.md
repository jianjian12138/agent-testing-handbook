# 07 · 可观测与生产监控：从"评过"到"持续可信"

> 目标：5 天（阶段四左翼）。
> 离线评测只证明"发布前那一刻是好的"。**真正的 Agent 测试，发生在它上线之后。** 这一篇讲怎么把测试能力延伸到生产，形成闭环。

---

## 7.1 为什么离线评测不够

传统自动化里，你跑完回归套件绿了，就敢发。Agent 不行，原因有三（呼应文档 01 的本质差异）：

1. **分布漂移**：模型、知识库、下游工具都在变，今天绿的用例下周可能红。
2. **长尾爆发**：离线集覆盖不到的边缘场景，生产流量里天天撞。
3. **错误传播**：一个工具失败被 Agent "圆"成错误答案，离线用例没覆盖这条路径。

所以生产环境需要**在线可观测 + 在线评测 + 失败回流**三件套。

---

## 7.2 OpenTelemetry：Agent 的"调用树 X 光"

OTel 是业界标准的分布式追踪协议。给 Agent 每层（LLM 调用 / 工具调用 / 规划步骤）打 Span，就能拿到完整 Trace。

```
一次用户对话的 Trace 结构：

[Span: conversation]  (总耗时 8.2s, 成本 ¥0.03)
 ├─ [Span: plan]        规划：拆成 3 步         (0.4s)
 ├─ [Span: llm_call]     调用模型决策           (1.1s)
 ├─ [Span: tool_query_order]  调用工具          (0.6s)  ← 这里慢/失败重点看
 ├─ [Span: llm_call]     综合结果生成答案       (0.9s)
 └─ [Span: reflect]      自我反思校验           (0.3s)
```

**Agent 测试视角下 OTel 的三个用途**：

| 用途 | 说明 | 对应文档 |
| --- | --- | --- |
| 失败定位 | 哪一步的工具超时/报错，精准到 Span | 文档 02 失效点 |
| 成本/性能基线 | 每次对话的 token、耗时、钱 | 文档 03 三维框架 |
| 评测数据源 | Trace 直接喂给在线评分器 | 本节 7.3 |

```python
# 用 OTel SDK 给工具调用打 Span（示意）
from opentelemetry import trace
tracer = trace.get_tracer("agent")

with tracer.start_as_current_span("tool_query_order") as span:
    span.set_attribute("tool.name", "query_order")
    span.set_attribute("tool.args", order_id)
    try:
        result = query_order(order_id)
        span.set_attribute("tool.success", True)
    except Exception as e:
        span.set_attribute("tool.success", False)
        span.record_exception(e)
        raise
```

> Langfuse / Opik 都兼容 OTel，等于你打一次 Span，两边都能看。

## 7.3 在线评测：生产流量自动打分

把离线评测的 Grader（文档 04）搬到线上，对**采样**的生产 Trace 自动打分：

```
生产流量 ──► OTel Trace ──► 在线评分器(LLM-as-Judge) ──► 分数流
                                                    │
                                          ┌─────────┴─────────┐
                                          ▼                   ▼
                                   异常告警(忠实度<阈值)   失败用例回流(7.4)
```

**在线评测要采样，不要全量**（成本考虑）：
- 高频低风险：采样 1–5%
- 高风险操作（支付/删除）：100% 评测 + 人工复核兜底

**在线重点盯三类指标**（比离线更敏感）：
- **Faithfulness（忠实度）**：生产环境编造率往往比离线高，因为长尾问题多。
- **工具失败率**：某个下游工具开始频繁报错，评分器会先一步发现"圆谎"答案。
- **成本/耗时突增**：模型升级或提示词改动常带来隐性成本爆炸。

## 7.4 失败用例回流：让测试集自己长大

这是把"传统回归测试"思路搬到 Agent 的最关键一步，也是你老本行的延伸：

```
生产失败 Trace
   │  (忠实度低 / 工具失败 / 用户差评)
   ▼
自动入库到"候选数据集"
   │  (人工 or Agent-as-Judge 审核)
   ▼
标注 expected_output / expected_trace
   │
   ▼
进入回归测试集（文档 05 的"只增不减"）
   │
   ▼
下次 CI 自动回归  ←── 闭环
```

**回流节奏建议**：
- 每周清理一次"候选数据集"，能标定的进黄金集。
- 同一类失败出现 ≥3 次，必须进回归集（防复现）。
- 这正好对应文档 05 的"数据集运营节奏"。

## 7.5 瑞士奶酪模型：生产监控的分层防御

Anthropic 提出：单一防护必有漏洞，要像瑞士奶酪一样**多层叠加**，让漏洞不重叠。

```
层1  评测集门禁      (发布前拦截已知问题)
层2  在线评分器      (生产实时打分，忠实度/工具失败率)
层3  用户反馈回路    (差评/投诉 → 回流)
层4  运行时护栏      (敏感操作二次确认、输出过滤)
层5  人工抽检        (高风险场景 100% 人审)
```

每一层都有洞，但五层叠起来，漏到用户的缺陷概率极低。**做平台时，这五层就是你要搭的监控面板分区。**

## 7.6 告警与值班：把评测变成 SRE 语言

生产监控最终要落到"谁来处理"。建议把 Agent 指标翻译成 SLO：

| 指标 | SLO 示例 | 触发动作 |
| --- | --- | --- |
| 在线忠实度 | ≥ 95%（周滚动） | 跌破 → 告警 + 冻结本次模型/提示词变更 |
| 工具失败率 | ≤ 2% | 超 → 查下游依赖 |
| P95 耗时 | ≤ 10s | 超 → 性能回归排查 |
| 单位对话成本 | ≤ ¥0.05 | 超 → 提示词/模型优化 |

> 你做传统测试平台时一定配过监控告警，这一套直接平移，只是指标换成 Agent 的语言。
